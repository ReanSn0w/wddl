# AGENTS.md

## Назначение проекта

`wddl` — односторонний загрузчик файлов с удалённого WebDAV-хранилища на локальный диск. Изначальный целевой сервис — MyPikPak: его WebDAV не допускает `POST`, поэтому проект не должен превращаться в обычный двусторонний Cloud Sync и не должен требовать загрузки данных на сервер.

Штатный путь работы использует только чтение каталога, чтение файла диапазоном и локальную запись. Изменение удалённого хранилища допускается только через явно включённое удаление уже скачанных файлов.

## Стек и команды

- Язык: Go; модуль `github.com/ReanSn0w/wddl`.
- Требуемая версия по `go.mod` и Dockerfile: Go 1.24 или новее.
- Основная проверка: `go test ./...`.
- Статический анализ: `go vet ./...`.
- Сборка CLI: `go build -o /tmp/wddl ./cmd/webdav`.
- Форматирование изменённых Go-файлов: `gofmt -w <files>`.
- Локальный запуск: `WEBDAV_USER=... WEBDAV_PASSWORD=... go run ./cmd/webdav --config ./config.yaml run`.
- Сборка контейнера: `docker build --build-arg TAG=<version> -t wddl .`.

`go test -race ./...` входит в обязательные проверки изменений конкурентного кода. Также `.github/workflows/ci.yml` пока устанавливает Go 1.21, что расходится с `go 1.24.0` в `go.mod`; при изменении CI версии нужно синхронизировать. Публикация контейнера настроена для тегов `v*` и ветки `master`, хотя основная ветка репозитория сейчас называется `main`.

## Структура

- `cmd/webdav` — типизированное дерево `go-flags`, human/JSON-вывод и bootstrap `run`.
- `pkg/config` — строгая загрузка, значения по умолчанию и валидация версионированной YAML-конфигурации.
- `pkg/control` — `/v1` HTTP/JSON-контракт, Unix client/server и неблокирующий broker событий.
- `pkg/daemon` — единственный владелец WebDAV, очереди, индекса и engine; scheduler, status, cleanup и reload.
- `pkg/engine` — поиск новых файлов, параллельные отменяемые загрузки и runtime progress.
- `pkg/files` — рекурсивный обход WebDAV, range-загрузка, возобновление по частям, сборка итогового файла и опциональный `DELETE` на сервере.
- `pkg/localindex` — атомарно обновляемый индекс дополнительных read-only библиотек по точной паре «имя + размер»; положительный результат всегда перепроверяется через `stat`.
- `pkg/queue` — потокобезопасная очередь в памяти с атомарным сохранением версионированного JSON-снимка; записи адресуются ID файла. Один queue-файл поддерживает только один процесс.
- `Dockerfile` — многостадийная статическая сборка и scratch runtime.
- `config.example.yaml` — полная схема постоянной конфигурации без credentials и действий запуска.

## Поток данных и важные инварианты

1. `run` строго загружает YAML, читает credentials из env и создаёт единственные WebDAV-клиент, очередь, индекс и демон. Клиентские команды читают YAML только для `control.socket` и credentials не требуют.
2. Демон синхронно строит локальный индекс, затем сразу сканирует WebDAV и лишь после этого запускает воркеры. Периодические и ручные обходы идут через один scheduler.
3. `files.Scan` рекурсивно обходит `webdav.root`. Для каждого удалённого файла `engine.NewFile` строит:
   - ID как MD5 от `source + "_" + size`;
   - конечный путь как `download.destination` плюс путь относительно `webdav.root`;
   - каталог частей как `download.temp/<file-id>`.
4. По ожидаемому пути файл считается готовым при совпадении имени и размера. В дополнительных библиотеках совпадение определяется точной регистрозависимой парой «имя + размер» независимо от пути; перед использованием индекс повторяет `stat`. Контрольной суммы и сравнения времени модификации сейчас нет.
5. Новые задачи атомарно сохраняются в `queue.json`. `Queue.Chan` сразу выдаёт текущий снимок, просыпается при добавлении задачи и повторно выдаёт оставшиеся задачи каждые 3 секунды; `Engine` защищает один ID от одновременной повторной загрузки внутри процесса.
6. Загрузка начинается с задержкой 3 секунды и имеет до трёх попыток с паузами 2 и 4 секунды. Данные читаются через `ReadStreamRange` и сохраняются последовательными частями по 64 МиБ (`1.part`, `2.part`, ...).
7. Возобновление учитывает только непрерывную последовательность корректных по размеру частей от `1.part`. Некорректная следующая часть при продолжении перезаписывается.
8. После полной загрузки части валидируются, объединяются в `.merging`, синхронизируются, проверяются по итоговому размеру, копируются в `Dest`, после чего временный каталог удаляется. `moveFile` намеренно делает copy + fsync + remove, поэтому работает между разными файловыми системами.
9. Задача удаляется из JSON-очереди только после успешного завершения. При `download.remove_remote: true` затем удаляется и исходный удалённый файл.

Сохраняйте возможность продолжить загрузку после перезапуска: не удаляйте неполные `download.temp/<id>` и записи очереди при обычной ошибке. Не публикуйте конечный файл до полной проверки всех частей и размера.

## Конфигурация и режимы удаления

Постоянные настройки находятся в YAML версии `1`; эталон — `config.example.yaml`. Вне файла остаются путь `--config`/`WDDL_CONFIG` и обязательные только для `run` `WEBDAV_USER` и `WEBDAV_PASSWORD`. Не добавляйте env-override для полей YAML. Не помещайте credentials или действия запуска в YAML.

Поля схемы сгруппированы в `webdav`, `download`, `queue`, `existing_files`, `logging` и `control`. Duration-поля используют синтаксис `time.ParseDuration`. Не проверяйте существование `existing_files.roots` в `pkg/config`: доступность каталогов проверяется при запуске индекса.

Есть два режима удаления:

- `download.remove_remote: true` — обычный непрерывный загрузчик; после успешной загрузки или обнаружения подтверждённой локальной копии выполняет удаление исходника.
- `cleanup remote` — двухэтапная cleanup-команда через демон. Preview ничего не удаляет, confirm-токен криптографически случаен, короткоживущий и одноразовый; перед каждым `DELETE` повторно проверяются обе стороны.

Удаление на сервере — потенциально разрушительная операция. Любые изменения этой логики должны оставлять opt-in поведение, проверять соответствие локального файла и иметь тесты на несовпадение/ошибки. Не включайте удаление по умолчанию.

## Правила изменений

- Сохраняйте download-only модель для совместимости с PikPak: не добавляйте `POST`, `PUT`, `MKCOL` или обязательную удалённую запись в основной сценарий.
- Разделяйте удалённые и локальные пути. Для WebDAV-путей предпочтителен пакет `path` и `/`; для локальной файловой системы — `filepath`. Учитывайте `webdav.root`, вложенные каталоги и ведущие слеши.
- Не меняйте формулу ID, размер части или схему JSON очереди без плана совместимости: существующие `queue.json` и каталоги `download.temp` переживают перезапуски и являются пользовательским состоянием.
- Не открывайте один `queue.json` из нескольких процессов. Чтения выполняйте по снимку памяти, а мутации сохраняйте через временный файл, `fsync` и атомарное переименование до публикации нового состояния.
- Не считайте отсутствие файла единственной ошибкой `os.Stat`: ошибки прав, I/O и повреждения должны возвращаться или логироваться отдельно.
- Во всех циклах и горутинах сохраняйте корректное завершение по `context.Context`; при работе с каналами обрабатывайте их закрытие и не допускайте повторного запуска одной задачи.
- Не ломайте семантику `/v1`: успех и ошибка идут в едином envelope со stable error codes и HTTP status. Не добавляйте TCP-listener и не возвращайте credentials или secrets в control API.
- Закрывайте сетевые потоки и файловые дескрипторы на всех ветках ошибок. Итоговый файл не должен оставаться частично записанным под конечным именем.
- Не логируйте пароль или полный набор credentials. `.env`, `queue.json`, каталоги `Sync`/`test` и отладочные артефакты уже исключены через `.gitignore`.
- Следуйте существующему стилю: небольшие пакеты, явные интерфейсы на стороне потребителя, оборачивание ошибок через `%w`, лог-сообщения с уровнями в квадратных скобках.

## Тестирование изменений

Автоматические тесты покрывают `pkg/queue`, локальный индекс и его интеграцию с `pkg/engine` и `pkg/utils`. При изменении `pkg/engine`, `pkg/files` или `pkg/utils` добавляйте unit-тесты с fake-реализациями уже существующих интерфейсов; тесты не должны обращаться к настоящему PikPak/WebDAV и не должны требовать credentials.

Минимальные сценарии для загрузчика: файл меньше 64 МиБ, ровно кратный 64 МиБ, последняя неполная часть, продолжение с нескольких готовых частей, повреждённая часть, ошибка range-чтения, ошибка локальной записи, корректная сборка вложенного пути. Для движка проверяйте дедупликацию, совпадение/несовпадение локального размера, удаление задачи только после успеха и opt-in удаление удалённого файла.

Перед завершением изменения выполните как минимум:

```sh
gofmt -w <изменённые-go-файлы>
go test ./...
go vet ./...
go build -o /tmp/wddl ./cmd/webdav
```

Для правок, затрагивающих реальный WebDAV, отдельно опишите ручную проверку на тестовом каталоге. Никогда не подтверждайте `cleanup remote` для production-каталога без явного разрешения владельца.
