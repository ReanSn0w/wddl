# AGENTS.md

## Назначение проекта

`wddl` — односторонний загрузчик файлов с удалённого WebDAV-хранилища на локальный диск. Изначальный целевой сервис — MyPikPak: его WebDAV не допускает `POST`, поэтому проект не должен превращаться в обычный двусторонний Cloud Sync и не должен требовать загрузки данных на сервер.

Штатный путь работы использует только чтение каталога, чтение файла диапазоном и локальную запись. Изменение удалённого хранилища допускается только через явно включённое удаление уже скачанных файлов.

## Стек и команды

- Язык: Go; модуль `github.com/ReanSn0w/wddl`.
- Требуемая версия по `go.mod` и Dockerfile: Go 1.24 или новее.
- Основная проверка: `go test ./...`.
- Статический анализ: `go vet ./...`.
- Сборка CLI: `go build -o /tmp/wddl ./cmd/webdav`.
- Форматирование изменённых Go-файлов: `gofmt -w <files>`.
- Локальный запуск: `go run ./cmd/webdav` с переменными из `example.env` или соответствующими CLI-флагами.
- Сборка контейнера: `docker build --build-arg TAG=<version> -t wddl .`.

Не считайте `go test -race ./...` обязательным зелёным gate без дополнительной проверки: на Go 1.26/arm64 текущий `github.com/boltdb/bolt v1.3.1` падает в `checkptr` внутри зависимости. Обычные тесты, `go vet` и сборка проходят. Также `.github/workflows/ci.yml` пока устанавливает Go 1.21, что расходится с `go 1.24.0` в `go.mod`; при изменении CI версии нужно синхронизировать. Публикация контейнера настроена для тегов `v*` и ветки `master`, хотя основная ветка репозитория сейчас называется `main`.

## Структура

- `cmd/webdav/main.go` — CLI, разбор флагов/окружения, подключение к WebDAV, выбор обычного режима или разовой очистки.
- `pkg/engine` — оркестрация сканирования, постоянной очереди, параллельных загрузок и логирования прогресса. Интерфейсы `Scanner`, `Downloader` и `Queue` — основные границы для тестовых doubles.
- `pkg/files` — рекурсивный обход WebDAV, range-загрузка, возобновление по частям, сборка итогового файла и опциональный `DELETE` на сервере.
- `pkg/queue` — постоянная очередь в BoltDB; записи сериализуются как JSON и адресуются ID файла.
- `pkg/utils` — отдельная разовая очистка удалённых файлов, если локальная копия того же размера уже существует.
- `Dockerfile` — многостадийная статическая сборка и scratch runtime.
- `example.env` — пример основной конфигурации; не добавляйте реальные логины и пароли в репозиторий.

## Поток данных и важные инварианты

1. CLI создаёт `gowebdav.Client`, проверяет соединение и собирает `engine.Config`.
2. В обычном режиме движок запускает три фоновых контура: сканирование, выдачу задач воркерам и печать прогресса. Первое сканирование происходит после первого интервала `TIMEOUT`, а не сразу после запуска.
3. `files.Scan` рекурсивно обходит `INPUT`. Для каждого удалённого файла `engine.NewFile` строит:
   - ID как MD5 от `source + "_" + size`;
   - конечный путь как `OUTPUT` плюс путь относительно `INPUT`;
   - каталог частей как `TEMP/<file-id>`.
4. Уже существующий локальный файл считается готовым только по совпадению размера. Контрольной суммы и сравнения времени модификации сейчас нет.
5. Новые задачи сохраняются в BoltDB. `Queue.Chan` перечитывает очередь каждые 3 секунды, а `Engine` защищает один ID от одновременной повторной загрузки внутри процесса.
6. Загрузка начинается с задержкой 3 секунды и имеет до трёх попыток с паузами 2 и 4 секунды. Данные читаются через `ReadStreamRange` и сохраняются последовательными частями по 64 МиБ (`1.part`, `2.part`, ...).
7. Возобновление учитывает только непрерывную последовательность корректных по размеру частей от `1.part`. Некорректная следующая часть при продолжении перезаписывается.
8. После полной загрузки части валидируются, объединяются в `.merging`, синхронизируются, проверяются по итоговому размеру, копируются в `Dest`, после чего временный каталог удаляется. `moveFile` намеренно делает copy + fsync + remove, поэтому работает между разными файловыми системами.
9. Задача удаляется из BoltDB только после успешного завершения. При `CLEAR_REMOTE=true` затем удаляется и исходный удалённый файл.

Сохраняйте возможность продолжить загрузку после перезапуска: не удаляйте неполные `TEMP/<id>` и записи очереди при обычной ошибке. Не публикуйте конечный файл до полной проверки всех частей и размера.

## Конфигурация и режимы удаления

Основные переменные окружения: `WEBDAV_SERVER`, `WEBDAV_USER`, `WEBDAV_PASSWORD`, `INPUT`, `TEMP`, `OUTPUT`, `DB_FILE`, `THREADS`, `TIMEOUT`, `CLEAR_REMOTE`. Их CLI-эквиваленты видны через `go run ./cmd/webdav --help`.

Переменная `P_SIZE` из текущего `example.env` кодом не читается: размер части задан константой `partitionSize` в `pkg/files/files.go`. Не документируйте `P_SIZE` как рабочую настройку, пока она действительно не будет реализована.

Есть два разных флага, их нельзя смешивать:

- `CLEAR_REMOTE=true` / `--clear-remote` — обычный непрерывный загрузчик; после успешной загрузки каждого файла выполняет удаление исходника.
- `UTIL_CLEAR_REMOTE=true` / `--util.clear-remote` — одноразовая утилита: рекурсивно находит удалённые файлы, проверяет локальную копию в `OUTPUT` только по размеру, удаляет совпавшие удалённые файлы и завершает процесс. В этом режиме очередь и загрузчики не запускаются.

Удаление на сервере — потенциально разрушительная операция. Любые изменения этой логики должны оставлять opt-in поведение, проверять соответствие локального файла и иметь тесты на несовпадение/ошибки. Не включайте удаление по умолчанию.

## Правила изменений

- Сохраняйте download-only модель для совместимости с PikPak: не добавляйте `POST`, `PUT`, `MKCOL` или обязательную удалённую запись в основной сценарий.
- Разделяйте удалённые и локальные пути. Для WebDAV-путей предпочтителен пакет `path` и `/`; для локальной файловой системы — `filepath`. Учитывайте корневой `INPUT`, вложенные каталоги и ведущие слеши.
- Не меняйте формулу ID, размер части или схему JSON очереди без плана совместимости: существующие `.db` и каталоги `TEMP` переживают перезапуски и являются пользовательским состоянием.
- Не считайте отсутствие файла единственной ошибкой `os.Stat`: ошибки прав, I/O и повреждения должны возвращаться или логироваться отдельно.
- Во всех циклах и горутинах сохраняйте корректное завершение по `context.Context`; при работе с каналами обрабатывайте их закрытие и не допускайте повторного запуска одной задачи.
- Закрывайте сетевые потоки и файловые дескрипторы на всех ветках ошибок. Итоговый файл не должен оставаться частично записанным под конечным именем.
- Не логируйте пароль или полный набор credentials. `.env`, базы `*.db`, каталоги `Sync`/`test` и отладочные артефакты уже исключены через `.gitignore`.
- Следуйте существующему стилю: небольшие пакеты, явные интерфейсы на стороне потребителя, оборачивание ошибок через `%w`, лог-сообщения с уровнями в квадратных скобках.

## Тестирование изменений

Сейчас автоматические тесты покрывают в основном `pkg/queue`. При изменении `pkg/engine`, `pkg/files` или `pkg/utils` добавляйте unit-тесты с fake-реализациями уже существующих интерфейсов; тесты не должны обращаться к настоящему PikPak/WebDAV и не должны требовать credentials.

Минимальные сценарии для загрузчика: файл меньше 64 МиБ, ровно кратный 64 МиБ, последняя неполная часть, продолжение с нескольких готовых частей, повреждённая часть, ошибка range-чтения, ошибка локальной записи, корректная сборка вложенного пути. Для движка проверяйте дедупликацию, совпадение/несовпадение локального размера, удаление задачи только после успеха и opt-in удаление удалённого файла.

Перед завершением изменения выполните как минимум:

```sh
gofmt -w <изменённые-go-файлы>
go test ./...
go vet ./...
go build -o /tmp/wddl ./cmd/webdav
```

Для правок, затрагивающих реальный WebDAV, отдельно опишите ручную проверку на тестовом каталоге. Никогда не используйте production-каталог с `CLEAR_REMOTE` или `UTIL_CLEAR_REMOTE` без явного разрешения владельца.
