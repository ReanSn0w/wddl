## Что мы делаем?

Переводим финальный Docker-образ со `scratch` на закреплённую поддерживаемую версию Alpine, устанавливаем бинарник как `/usr/local/bin/wddl`, запускаем контейнер командой `wddl run` от непривилегированного пользователя и документируем безопасную подстановку UID/GID в Synology Compose. Обновляем CI для публикации одного GHCR manifest с вариантами `linux/amd64` и `linux/arm64`: текущий Synology NAS использует `amd64`, а ARM64-вариант сохраняется для переносимости образа на другие устройства.

## Для чего мы делаем?

Текущий scratch-образ минимален, но не содержит shell, а приложение расположено как `/srv/app`, что неудобно для вызова новых управляющих команд через интерфейс Synology. Текущий GitHub Actions workflow уже создаёт подходящий для имеющегося `amd64` NAS образ, однако публикация дополнительного ARM64-варианта делает релиз переносимым без отдельных тегов. Alpine добавит `/bin/sh` и базовые BusyBox-утилиты, а размещение `wddl` в стандартном `PATH` позволит вызывать команды из любой директории. Запуск без root и явные ограничения контейнера компенсируют увеличение runtime-поверхности.

## План

- [ ] Перестроить многостадийный Dockerfile
  - [ ] Закрепить поддерживаемые minor-версии Go builder image и Alpine runtime image вместо плавающего `latest`.
  - [ ] Синхронизировать версию Go builder с директивой `go` в `go.mod`.
  - [ ] Использовать `COPY` для `go.mod` и `go.sum` отдельным слоем до копирования исходников.
  - [ ] Загружать Go-модули отдельным кэшируемым шагом сборки.
  - [ ] Использовать аргументы BuildKit `BUILDPLATFORM`, `TARGETOS` и `TARGETARCH` для кросс-компиляции.
  - [ ] Собирать бинарник с `CGO_ENABLED=0`, `-trimpath` и существующим внедрением revision через `-ldflags`.
  - [ ] Копировать готовый бинарник в `/usr/local/bin/wddl` финального образа.
  - [ ] Установить в runtime только `ca-certificates`, сохранив встроенные `/bin/sh` и BusyBox-утилиты Alpine.
  - [ ] Не устанавливать Bash, curl, компилятор или пакетный кэш без отдельной эксплуатационной необходимости.

- [ ] Настроить стандартный запуск CLI внутри контейнера
  - [ ] Использовать exec-form `ENTRYPOINT ["wddl"]` без промежуточного shell.
  - [ ] Использовать `CMD ["run"]` для запуска демона по умолчанию.
  - [ ] Сохранить возможность переопределить CMD для автономных команд `version` и `config validate`.
  - [ ] Проверить, что `wddl`, `wddl --help` и вложенные команды находятся через `PATH` из любой рабочей директории.
  - [ ] Установить стабильный `WORKDIR` в записываемом каталоге состояния, согласованном с YAML-примером.
  - [ ] Удалить старый путь `/srv/app` и не оставлять вторую копию бинарника.

- [ ] Добавить безопасного пользователя по умолчанию
  - [ ] Создать в Alpine системные группу и пользователя `wddl` с закреплёнными числовыми UID/GID.
  - [ ] Переключить финальный образ на `USER wddl:wddl`.
  - [ ] Создать только небольшие служебные каталоги образа и назначить их пользователю `wddl` на этапе сборки.
  - [ ] Не выполнять рекурсивный `chown` примонтированных download/library каталогов при старте контейнера.
  - [ ] Не запускать entrypoint от root ради динамического изменения UID/GID.
  - [ ] Обеспечить понятную ошибку приложения, если настроенные output/temp/state каталоги недоступны на запись.

- [ ] Поддержать UID/GID владельца каталогов Synology через Compose
  - [ ] Добавить в пример Compose поле `user: "${WDDL_UID:-10001}:${WDDL_GID:-10001}"` с дефолтами, совпадающими с пользователем образа.
  - [ ] Пояснить, что Compose не выполняет `$(id -u)` или `$(id -g)` внутри YAML.
  - [ ] Описать ввод числовых `WDDL_UID` и `WDDL_GID` в окружении проекта Synology или его `.env`.
  - [ ] Не передавать `WDDL_UID` и `WDDL_GID` внутрь приложения, поскольку они нужны Compose только для выбора пользователя процесса.
  - [ ] Проверить доступ выбранного UID/GID на чтение WebDAV-конфига и дополнительных библиотек.
  - [ ] Проверить доступ выбранного UID/GID на запись в output, temp и каталог состояния.
  - [ ] Предупредить, что произвольный numeric UID может не иметь имени в `/etc/passwd`, но это не мешает выполнению `wddl` и `/bin/sh`.

- [ ] Разделить контейнерные точки монтирования по назначению
  - [ ] Выделить read-only mount для `config.yaml`.
  - [ ] Монтировать дополнительные локальные библиотеки только с `:ro`.
  - [ ] Выделить writable mount для конечных загрузок.
  - [ ] Выделить writable mount для временных частей.
  - [ ] Выделить writable mount для `queue.json` и Unix-сокета либо документировать их размещение в общем state-каталоге.
  - [ ] Не объявлять пользовательские медиакаталоги через жёстко заданные инструкции `VOLUME` в Dockerfile.
  - [ ] Согласовать container paths в Compose-примере с `config.example.yaml`.

- [ ] Усилить runtime-ограничения в рекомендуемом Compose
  - [ ] Добавить `read_only: true` для корневой файловой системы контейнера.
  - [ ] Добавить небольшой writable `tmpfs` для `/tmp`, если он требуется Alpine или диагностическим командам.
  - [ ] Добавить `cap_drop: [ALL]`.
  - [ ] Добавить `security_opt: [no-new-privileges:true]`.
  - [ ] Не публиковать управляющий Unix-сокет как TCP-порт.
  - [ ] Не использовать `privileged: true` и не монтировать Docker socket.
  - [ ] Проверить исходящее HTTPS-соединение с WebDAV при полностью удалённых Linux capabilities.

- [ ] Удалить устаревшие настройки runtime-образа
  - [ ] Удалить встроенные гостевые значения `WEBDAV_USER` и `WEBDAV_PASSWORD`.
  - [ ] Удалить старые `ENV INPUT`, `TEMP`, `OUTPUT`, `THREADS`, `TIMEOUT` и `DB_FILE` после выполнения YAML-плана.
  - [ ] Оставить только нейтральное значение `WDDL_CONFIG`, если для контейнера нужен путь по умолчанию.
  - [ ] Удалить старую инструкцию `VOLUME ["/data"]`, если она конфликтует с явными mounts в Compose-документации.
  - [ ] Проверить отсутствие credentials и пользовательских путей во всех слоях итогового образа.
